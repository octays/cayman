# Cayman 性能、可靠性与实时增量同步方案

> 当前交付更新：`send SOURCE` / `receive TARGET` 已默认选择 croc 中继；仅显式 `--listen` / `--connect` 使用直连。已实现 Rust 中继接入适配、SPAKE2 短码配对、端到端 TLS、固定块增量、轮询同步、冲突保护和原子落盘。中继适配已通过独立 Go 算术向量与内存协议测试，真实 Go relay / 公共节点互操作尚待验证。短码配对已接入，自动重连、删除传播和双向同步仍未实现。当前用法见 [README](../README.md)，兼容性边界见 [中继适配说明](relay-implementation.md)。

日期：2026-10-14。本文扩展 [基础实施方案](implementation-plan.md)，属于待实现设计，没有经过性能实测。同步阶段与基础方案存在差异时，以本文明确标注的同步规则为准；一次性发送行为保持独立。

实现范围：仅做跨机器同步，不提供 local-sync。当前已实现中继接入与单向轮询增量同步；下述索引缓存、原生监听、自动恢复和双向同步等仍待实现，实际 CLI 见 [README](../README.md)。

## 1. 产品范围与关键决策

保留现有 Go croc 中继兼容路线，新增目录级 `sync` 模式。目标是首次比较两端内容、只传输缺失块，随后持续检测变化并同步；断网后能自动重新认证、重新比对并恢复。它不等同于文件传输的断点续传，也不要求换用 libp2p。

同步按两阶段实现：先交付单向安全同步，再交付双向安全同步。尚未确定用户最终默认模式，暂设 `one-way-safe`；协议和持久化模型从第一阶段保留双方版本信息，避免后续重写。双向同步是本方案的正式后续交付项。默认不传播删除，镜像删除需配置显式开启。

| 能力 | 一次性 send/receive | 持续 sync |
| --- | --- | --- |
| 身份 | 每次短期暗号配对 | 首次短期暗号配对并授权持久关系，之后设备认证 |
| 内容判断 | 单文件完整性及续传进度 | 相对路径、版本、完整内容摘要与块列表 |
| 重连 | 重新分享暗号 | 已授权设备自动重连，不复用短暗号 |
| 落盘 | 默认不覆盖目标 | 按同步模式有条件更新，保留冲突和历史版本 |
| 生命周期 | 完成后退出 | 首次收敛后监听，周期性校验并持续运行 |

同步正确性的承诺是：文件停止变化、两端在线、存储可写、没有未解决冲突时，最终收敛。实时表示尽快触发，不能保证任意网络和持续写入负载下的固定延迟。

## 2. 性能优化：先减少工作量，再提高吞吐

### 2.1 优先级与实现策略

| 优先级 | 优化项 | 做法与收益 | 约束 |
| --- | --- | --- | --- |
| P0 | 避免整文件重传 | 整文件摘要相同直接跳过；否则比较块列表 | 摘要必须对应稳定版本，不能只比较 mtime |
| P0 | 有界流水线 | 扫描/读盘 → 摘要/压缩 → 加密/网络 → 验证/写盘并行 | 按字节预算背压，不能无限 spawn |
| P0 | 缓冲复用 | `BytesMut`/缓冲池、原地 AEAD、合并小写入 | 从池分配也计入总内存预算 |
| P0 | 批量持久化 | 多块共享一次同步与状态事务 | ACK 必须区分收到与持久化 |
| P1 | 小文件批处理 | 分页清单、小文件请求批次、单连接复用 | 单文件仍有独立版本及提交结果 |
| P1 | 有限并发 | 初始 4 个活动文件、2 个哈希任务，按环境调节 | 大文件顺序读优先，避免机械盘随机寻道 |
| P1 | CDC 内容分块 | 大文件插入/删除后复用未变内容 | 降低网络流量，不消除重新读取源文件成本 |
| P1 | 自适应压缩 | `zstd` 低级别逐块压缩，仅保留比原始块小的结果 | 压缩后加密；限制解压长度、窗口和 CPU |
| P2 | 目录 Merkle 索引 | 缓存子树摘要，跳过相同子树清单 | 索引必须先反映本地磁盘变化 |
| P2 | 直连/多连接 | 基准证明链路瓶颈后增加 | 单独通道认证、流控与顺序语义，不能复用 nonce |

客户端需处理明文摘要和加密，普通 `sendfile` 无法直接替代整个发送管线，不把“零拷贝”作为首版目标。保留 SHA-256 作为统一内容摘要，优先避免重复读取；有实测证据后再评估其他哈希算法，不能静默改变文件身份。

### 2.2 初始资源预算

以下均为可配置起点，不是已验证最优值：

- 每会话数据缓冲预算 64 MiB，另设索引缓存 64 MiB；TLS、数据库及运行时开销单独测量。进程总预算约束多个会话，不能给每个会话无限叠加额度。
- 块传输逻辑窗口初始 8 MiB、上限 32 MiB；收到持久化 ACK 后释放持久化窗口。接收端内存配额另通过 credit 控制，不能把 TCP 缓冲等同于可写磁盘容量。
- 固定块 1 MiB；CDC 初始最小 64 KiB、平均 256 KiB、最大 1 MiB。块大小与网络帧大小分离，建议数据消息拆成不超过 64 KiB 的片段，使控制消息可插队。
- 目录/块清单每页不超过 256 KiB，所有字段、页数和并发请求有独立上限。
- 数据读写、扫描、压缩分别设 semaphore；阻塞文件操作和 CPU 工作进入有限工作池，不占据网络任务。
- 批量刷盘初始为每 16 MiB 或每秒一次，文件完成时强制刷盘。恢复允许重传最后一个未确认批次。

窗口调优依据是带宽时延积，例如 100 Mbit/s、100 ms 的链路约需 1.25 MB 在途数据；还需考虑接收端刷盘间隔。逻辑窗口内允许多个未确认块，不能每块停等。双向流量共用连接时，取消、ACK、心跳和清单使用有界高优先级队列，数据按文件公平调度；TCP 的底层队头阻塞仍然存在。

压缩按完整内容块独立执行，内容摘要始终基于未压缩内容。JPEG、归档及高熵块通常可尝试后直接跳过；不跨文件共享压缩字典。解码器在分配前检查预期原始长度，拒绝超出协商窗口的压缩流。[zstd Rust 文档](https://docs.rs/zstd/latest/zstd/)

## 3. 三层比对与增量算法

### 3.1 目录和整文件比对

每个目录定义随机 `folder_id`，本地路径由本机配置绑定。对端只能发送授权根目录下的相对路径，不能指定本机任意绝对路径。

清单记录包括：相对路径、类型、大小、展示用 mtime、内容 SHA-256、文件版本、分块方案 ID、块列表摘要及必要权限策略。mtime/大小/本地文件 ID 仅作为快速扫描缓存线索；不能据此认定首次两端文件内容相同。

首次扫描对双方普通文件计算内容身份，相同内容不发送文件数据。断线且本地 watcher 连续性不确定、索引重建或严格验证时重新核验内容。默认每 10 分钟带抖动进行元数据巡检，每 24 小时完成一轮有带宽预算的内容核验；超大目录显示核验积压，不能将尚未验证标记为已验证。提供 `--verify=full` 强制完整读取。

百万文件阶段增加目录 Merkle 索引：叶子绑定规范化路径、类型、内容/版本/删除状态，目录节点按字节排序哈希子项；规范化编码、域分离和忽略规则版本固定。根相同可跳过清单交换，根不同递归比较。Merkle 树负责定位差异，文件内容分块负责降低差异文件的传输量，二者不是替代关系。

### 3.2 文件内差量

| 算法 | 适用点 | 限制 | Cayman 决策 |
| --- | --- | --- | --- |
| 固定块 + 强摘要 | 简单、顺序改写和追加 | 文件前部插入可能使后续全部错位 | 首个可交付版本 |
| FastCDC + 强摘要 | 插入/删除后可重新对齐，大文件块复用 | 扫描与块索引有 CPU/存储成本 | 第二个增量版本，正式计划支持 |
| rsync 弱滚动校验 + 强摘要 | 根据接收方旧文件寻找可复制区间 | 要维护另一套 signature/delta 协议 | 暂不与 CDC 同时实现，保留评估 |

rsync 的核心是找出目标端已有的相同区域并发送无法匹配的部分，并不承诺所有情况下“改 1 字节只传 1 字节”。固定块通常重传受影响块，CDC 还可能改变附近边界，另有清单和协议开销。[rsync 技术报告](https://rsync.samba.org/tech_report/)

FastCDC 只确定边界，不是密码学摘要。每块继续用 SHA-256，并固定算法代际、最小/平均/最大尺寸及相关参数为 `chunking_id`。Rust `fastcdc` 提供流式接口，可作为实现候选；跨版本块边界需要黄金向量保证。[FastCDC 文档](https://docs.rs/fastcdc/latest/fastcdc/)

首轮 CDC 策略：小于 1 MiB 文件按单块处理，其余使用上述 CDC 参数；具体阈值经基准调整。同一内容版本不得在传输中改变分块方案。接收方用 `(chunking_id, hash, length)` 查询该同步根内已授权的本地数据，复制已有块，只请求缺失块；没有可复用内容或预估差量开销接近全量时，退回整文件顺序传输。

### 3.3 重建与数据验证

```text
源文件稳定版本 → 内容/块清单 → 接收端比较本地块
→ 请求缺失块 → 校验每块 → 临时文件重建
→ 整文件摘要核对 → 持久化提交 → 更新双方基线
```

首版复用接收端现有文件和本次已验证临时块，不建立无限增长的全局块仓库。CDC 阶段可增加有配额的块缓存；缓存回收以活动清单、恢复任务和历史版本的引用为依据。

索引命中不代表数据可信，本地复用块也要在复制时核对摘要。块请求必须绑定已授权 `folder_id`、文件版本与清单成员，不能提供“任意哈希读取全磁盘”的接口。文件最后仍校验整文件摘要，清单相等不代替磁盘验证。

网络少传不意味着磁盘少写：安全临时文件重建通常仍需读取复用块、写入新文件并最终校验。reflink 等优化仅在平台支持和正确性验证后启用。

## 4. 实时检测与变化收敛

使用 `notify` 作为变化提示，实际文件状态通过重新扫描确认。网络文件系统可能不产生通知，大目录也可能丢事件，需支持轮询回退。[notify 已知限制](https://docs.rs/notify/latest/notify/#known-problems)

启动顺序：先建立 watcher 并开始收集脏路径，再进行初始扫描，最后重扫扫描期间被标脏的路径。处理事件时不依赖严格顺序，也不把 rename 事件当作可信的完整操作日志。

- 默认按路径 500 ms 防抖；累计 2 秒后尝试扫描，持续变化文件标记为忙并退避，不反复发布混合版本。
- 事件入有界队列；溢出只设置可靠的 `rescan_required` 标志，随后执行全目录扫描，不能静默丢掉变化。
- watcher 失效、进程恢复、系统唤醒、根目录重挂载时重新扫描。NFS/不支持监听的路径用 polling，并明确增加的发现延迟。
- 源文件读前后比较打开句柄的大小、mtime 和文件身份，读期间遇到变化则丢弃候选版本。发送块时核对候选块摘要；块已改变则重新扫描，不把多个版本拼成一个版本。
- 连续写入数据库、虚拟机磁盘等不能仅靠防抖获得一致快照；要求应用导出、暂停写入或文件系统快照。普通文件 stat 检查不是事务快照保证。
- 文件事件先更新持久化索引和待办任务，再发布变更；多个尚未发送的同路径更新可合并成最新期望状态。已提交的版本历史及删除状态不得随意抹除。

文件 watcher 加周期扫描、块校验加临时文件提交是成熟同步工具采用的组合，适合作为工程参考。[Syncthing 同步机制](https://docs.syncthing.net/users/syncing.html)

## 5. 模式、冲突与删除语义

### 5.1 首次合并和单向安全模式

首次两端同名且内容不同的文件没有共同基线，默认标记冲突并暂停该路径，不根据 mtime 猜测谁更新。提供预览和显式 `prefer-source` 决策，将被替换版本先移入历史区。目标端独有文件默认保留。

进入正常同步后保存最近共同提交的基线。源端变化且目标仍等于基线时更新；目标被本地修改则保留目标文件，将远端候选保存在冲突区并报告。其他无冲突文件继续同步。这里的冲突副本不会被当成新源文件再次传播。

### 5.2 双向安全模式

每台设备有持久化身份，每个路径维护版本向量 `{device_id: counter}`，本地编辑在事务中增加本设备计数；应用远端版本不递增本地编辑计数。

- 版本相等且内容相同：已同步。
- 一方向量严格支配另一方：在本地基线未变化条件下接受较新版本。
- 向量不可比较：并发编辑，保留两份内容并报告冲突；内容相同可合并向量，不重传内容。
- 同版本却不同内容：索引损坏或协议异常，停止该路径并重新验证。
- 删除与修改并发、同路径文件与目录并发：都按冲突处理，不自动让删除获胜。

显式冲突解决生成一个支配所有冲突版本的新向量。墙上时钟只用于显示，不用于判定因果新旧。两端可参考共同基线做三方比较；Mutagen 的基线比较与安全同步模式是可参考的实现思路。[Mutagen 同步设计](https://mutagen.io/documentation/synchronization/)

初始双向版本仅支持两设备、单目录对；不承诺多设备网状收敛。每目录由稳定设备 ID 选出连接协调端、限制一条活动会话；连接角色与文件流向分离，避免双方同时重连把自己的两个 socket 配成一对。

### 5.3 删除、重命名和跨平台边界

默认 `--delete=off`。启用 `--delete=tracked` 后只传播已经共同管理的路径删除；目标独有文件仍保留。严格镜像可另设 `--delete=mirror`，首次必须展示额外删除集合，不能因远端清单缺页或扫描失败把整个目录判断为空。

删除先形成有版本的 tombstone，接收端将内容移入隔离历史区，再记录提交。根目录消失、磁盘未挂载、权限拒绝都标记“根不可用”，暂停任务及删除传播。大批删除超过配置阈值时暂停该批并要求明确解除，不默认永久清除历史区。

重命名初版作为新路径创建与旧路径删除，通过块复用避免重传；禁用删除时旧路径保留，明确展示这一结果。优化的 rename 必须携带源路径期望版本及目标不存在条件，不能仅靠操作系统文件 ID 推断跨设备身份。

初版仅同步普通文件和目录；符号链接、设备文件、socket 和 FIFO 拒绝或明确跳过。硬链接按独立文件处理，权限仅同步显式允许的普通位，不传播所有者、特权位和 ACL。UTF-8 路径逐组件验证；非 UTF-8 名称、大小写折叠冲突、Unicode 规范化冲突及 Windows 保留名明确报告，不能静默合并。

## 6. 持久化、幂等与崩溃恢复

### 6.1 索引和日志

目录同步使用 SQLite，经 `rusqlite` 调用，默认 WAL + `synchronous=FULL`、事务批处理和有限 `busy_timeout`。数据库放在本地应用状态目录，不能放进同步目录或网络挂载；WAL 的共享内存机制不适合跨机器网络文件系统。[SQLite WAL](https://www.sqlite.org/wal.html) · [rusqlite 文档](https://docs.rs/rusqlite/latest/rusqlite/)

建议表：`folders`、`peers`、`entries`、`blocks`、`changes`、`peer_cursors`、`operations`、`conflicts`。私钥单独保存在系统凭据存储或受限权限文件，不能混入可导出的索引。

变更标识为 `(folder_id, origin_device, index_epoch, sequence)`；文件另有内容版本。数据库重建生成新 epoch，强制清单重新对账，不能沿用丢失的计数器。应用应备份身份与因果元数据；二者无法恢复时重新配对，以新身份处理，不能伪造已确认历史。

消息交付采用至少一次，接收端用 `op_id` 和期望基线幂等应用。ACK 丢失后可查询提交结果或比较已提交版本，不能再次产生历史副本或重复执行删除。日志仅在对端已确认后裁剪；离线太久、游标落在已清理区间则执行完整对账，不能把过期旧清单当成新写入。

### 6.2 文件系统与数据库的跨域提交

数据库事务不能与文件 rename 自动组成原子事务，需要可恢复状态机：

```text
Planned → Staging → DataDurable → CommitIntent → Installed → Committed
```

1. 记录操作、目标基线、期望新摘要和随机临时文件标识。
2. 重建临时文件、验证整文件、同步数据，持久化 `DataDurable`。
3. 验证当前目标仍匹配期望基线；不匹配转为冲突。
4. 将可恢复的历史版本引用和提交意图写入数据库并同步，随后执行平台适配的安装/替换操作，同步受影响目录。
5. 事务更新正式索引、操作状态及对端游标，之后才发 `CommitAck`。

崩溃恢复按状态和磁盘摘要判定：目标已是期望新内容则补记提交；仍是旧版本则恢复安装；不符合两者则保留现场并报告冲突。不能仅因数据库存在一行就声称文件已持久化。

一般跨平台文件系统不提供“按内容摘要比较后原子替换”的通用 CAS。每根目录用进程锁避免多个 Cayman 写者；外部应用仍可能在检查与替换间写入。首版明确以受管理的接收目录获得强提交语义；需要本地并发编辑的双向模式使用平台文件锁/交换、历史保留及提交后复查尽量发现竞争，但不承诺任意外部写入下的零丢失事务快照。数据库和 VM 文件需专门快照策略。

历史区、临时数据、块缓存均有容量预算。空间不足时停止新任务并保持旧文件；历史未成功保存时不得继续覆盖。超额清理只能删除没有活动引用且已过保留期的数据，不能先删除恢复所需内容。

## 7. 长期配对、重连与密钥生命周期

一次性传输仍按基础方案使用短暗号。持续同步不能反复使用同一个低熵暗号无限重试，也不能要求每次断线都人工输入新暗号。

`send` / `receive` 的首次短期 PAKE 完成后，在已认证加密通道内交换并确认双方设备证书指纹、随机配对 ID、256 位 rendezvous secret、目录授权、角色和删除策略。仅本地显式创建的 sync 配对持久保存授权；普通 send 不自动授予长期目录访问。

后续连接完成 croc 接入后，使用 TLS 1.3 双向设备认证。推荐 `rustls`/`tokio-rustls`；信任范围仅限配对时固定的证书/公钥，并仍验证握手签名与证书用途，禁止使用接受任意证书的 verifier。首次版本关闭 0-RTT 和会话恢复，每次重新握手获取新流量密钥；轮换证书通过旧认证关系确认或重新配对。固定证书身份承载块同步可参考 Syncthing 的分层设计，但不复刻 BEP 协议。[rustls](https://docs.rs/rustls/latest/rustls/) · [Syncthing BEP](https://docs.syncthing.net/specs/bep-v1.html)

同步通道明确为 `cayman-sync/1`，协议内容位于 TLS 内，不再叠加基础方案的自定义 AES-GCM 记录层。复用文件消息编解码、流控、块校验及 croc 帧适配；适配器将 TLS 字节流分装进 croc 帧，禁止将明文业务消息旁路写入。TLS 配置协商完成后必须校验本地授权的 pair/folder/角色，拒绝协议降级。

TLS 长连接密钥更新由库支持的 TLS 1.3 机制完成；若所锁版本不能满足使用上限，主动安全重连，不无限使用原密钥。基础方案 64 GiB/2^24 限制仍适用于其自定义通道，不机械套用到 TLS。[TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446.html)

房间名由 rendezvous secret 通过带域分离的 HMAC 派生，秘密本身不发给中继；同一授权关系使用稳定路由标签，接受中继可关联该关系的元数据边界。它不是设备认证依据，中继抢房仍只能造成拒绝服务。凭据轮换需要双方确认新配置，不能由单端随机换房导致永久失联。

重连退避初始 1 秒、指数增长至 60 秒并加抖动；网络超时可重试，身份不匹配/授权撤销停止自动重试。保持每 pair 每端最多一个待连接。加密心跳每 15 秒，连续约 60 秒无对端进展判定失联；心跳不代表文件任务有进度，另设任务超时。同步会话允许重新查询和重传已记录操作，永远重新编码到新通道。

`sync unpair` 本地撤销授权并关闭活动连接，之后拒绝旧设备身份；本地删除凭据不能远程销毁对方数据。两端撤销及重新配对过程需可诊断。

## 8. 消息与模块扩展

| 消息 | 作用与约束 |
| --- | --- |
| SyncHello | 配对/目录 ID、模式、功能集、索引 epoch；授权后发送 |
| IndexPage / IndexEnd | 分页清单及快照编号，完整结束后才允许基于缺失判断删除 |
| ChangeBatch / CursorAck | 有序变更和持久化游标，检测缺口后补发或重新对账 |
| BlockManifestPage | 内容版本、块参数、偏移、长度、强摘要 |
| NeedBlocks / BlockData | 有界请求及分片响应，携带 request/op/file-version 标识 |
| Credit / DurableAck | 分离内存流控与持久化进度 |
| Commit / CommitAck / QueryOp | 基线条件提交、幂等结果和断线结果查询 |
| Conflict / Cancel / Ping / Pong | 可诊断冲突、取消及存活检测 |

所有变更绑定目录及文件版本；过时块可缓存但不能装入新版本。`Commit` 不是收到即覆盖的指令，接收端仍执行授权、路径、基线、摘要及落盘检查。

```text
src/sync/
  mod.rs          # 生命周期及同步模式
  scan.rs         # 首次/局部/周期扫描
  watch.rs        # notify、脏路径合并、溢出恢复
  index.rs        # SQLite 索引、epoch、游标
  chunk.rs        # 固定块、CDC、内容身份
  diff.rs         # 清单比较、缺失块计划
  reconcile.rs    # 基线、版本向量、冲突、tombstone
  scheduler.rs    # 并发、内存额度、公平调度
  apply.rs        # 提交日志及文件系统恢复
  session.rs      # 消息、重连、幂等
src/crypto/identity.rs  # 持久身份、配对授权、TLS 配置
```

新增依赖候选为 `notify`、`rusqlite`、`fastcdc`、`zstd`、`rustls`/`tokio-rustls`。具体版本及证书生成依赖在实施时验证、锁定；不因参考项目使用 libp2p 或其他 P2P 栈而额外引入第二套传输系统。

## 9. 计划 CLI

以下接口均待实现；首版持续同步以前台进程为主，暂不自动安装后台服务。

```bash
# 发送端仅配置本地源目录，显示短期暗号
cayman send ./source --name work --relay relay.example.com:9009

# 接收端交互输入暗号，独立配置本地目标并授权
cayman receive ./target --name work --relay relay.example.com:9009

# 双端启动已配对任务；默认 one-way-safe、delete=off
cayman sync run work --watch

# 只生成变化计划，不修改目标文件，也不提交对端游标
cayman sync run work --once --dry-run --verify=full

# 查看积压、冲突、对端状态与最近一次完整核验
cayman sync status work
cayman sync conflicts work

# 后续双向阶段：两端同意更新配对策略
cayman sync configure work --mode two-way-safe

# 撤销本地长期授权
cayman sync unpair work
```

发送端不接受接收端目标路径参数；各端只配置本地路径，状态目录由程序自动管理。首次配对后默认持续同步。

策略变更绑定配置代际，两端确认一致后生效；对端不能单方面扩大权限或启用删除。`--once` 完成一轮后退出；有冲突、跳过文件或根不可用不得报全部成功。`--watch` 可显示“已收敛”后继续监听，不把没有当前任务等同于退出。

## 10. 交付顺序与验收指标

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| S0 可测量基础 | 有界管线、指标、故障注入、基准工具 | 大文件内存有界，无逐块停等，持久化 ACK 正确 |
| S1 单次目录增量 | SQLite 索引、固定分块、单向安全、dry-run | 相同目录零文件载荷；变化只请求缺失块；冲突不静默覆盖 |
| S2 实时单向同步 | watcher+巡检、长期配对、TLS 重连、日志恢复 | 断线/杀进程后收敛，丢事件可修复，撤销身份不能重新接入 |
| S3 CDC 与规模优化 | FastCDC、压缩、块缓存、分页/Merkle | 插入/删除负载较固定块明显少传，资源仍受限 |
| S4 双向与删除 | 版本向量、冲突解决、tombstone、镜像选项 | 双端离线修改和删除冲突保留内容，重复操作不产生副作用 |

S0 与基础传输 P1–P4 交叉推进；S1 不依赖 CDC，S2 不等待 Merkle。S4 才对外宣称双向同步支持。部署生产持续同步前必须完成 S2 的身份、恢复和边界验证。

基准必须记录硬件、文件系统、构建 profile、版本、链路和冷热缓存。矩阵包含 1 GiB/10 GiB 大文件、10 万小文件、可压缩文本/不可压缩数据；修改场景包含 1 字节覆盖、头部插入、中部删除、尾部追加、重命名和 1% 文件变化。网络包括 10/100/1000 Mbit/s、RTT 1/50/200 ms、丢包及断线，磁盘覆盖 SSD 和慢盘。

记录实际网络总字节与纯文件载荷、哈希/读写字节、CPU、峰值 RSS、数据库/WAL 大小、fsync 延迟、变化发现至提交的 p50/p95、重连时间及恢复重传字节。增量效率以“网络文件载荷/整文件大小”表达，同时单独报告清单和认证开销。

初始功能和性能目标（待实测验证）：

- 已完成内容核验的相同目录再次对账，文件数据载荷为 0；仍允许必要清单和控制流量。
- 固定块文件原位修改 1 字节，仅发送对应块内容及必要元数据；CDC 插入案例记录受影响块数，不承诺固定字节比例。
- 健康本地 watcher、空闲任务队列、1 MiB 以下变更、RTT ≤ 50 ms、带宽 ≥ 100 Mbit/s、SSD 条件下，目标 p95 为文件稳定后 2 秒内提交。
- 事件溢出、静默漏事件、保留原大小/mtime 的修改分别通过溢出扫描、巡检、内容核验发现；不能把三者的延迟混为一个指标。
- 数据集增大时内存受配置预算约束，索引允许增长到磁盘；展示额外运行时开销，不能将 64 MiB 缓冲预算宣传成总 RSS 上限。
- 崩溃注入覆盖每个提交阶段；最终内容只能是验证后的版本或明确报告冲突，不出现损坏文件被标记成功。
- 双向测试涵盖离线同改、同内容并发、删除/改写冲突、目录/文件冲突、ACK 丢失、数据库重建、旧游标及 tombstone 回收后的重连。

## 11. 参考项目的使用边界

已核对的主要依据为 Syncthing 的分块/扫描/认证文档、Mutagen 的安全模式与共同基线设计、rsync 原始算法报告，以及所列 Rust 库官方文档。借鉴设计不表示与这些工具线级兼容。

用户已明确 p2sync 为 [davlgd/p2sync](https://github.com/davlgd/p2sync)，已补充 [文档层评估](p2sync-review.md)。其 README 提供了可参考的同步分层和算法方向，源码复用仍待实际代码及测试验证。性能基准增加 256 KiB 固定块及 BLAKE3 候选，默认算法暂不变更；同步核心保持与 croc/libp2p 等具体传输解耦。

rasync、syncx、bit-sync-esm、alice-sync 等仍为后续调研候选；未核实具体仓库、维护状态、许可证和安全实现，不据此作依赖承诺，也不引用其单字节变化的宣传数字作为 Cayman 验收依据。当前路径是在已选传输层上增加独立同步引擎。
